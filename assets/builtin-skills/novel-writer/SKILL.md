# 小说写作主线（单管线）

本作采用单一工作流：先恢复状态并最小读取，再完成初稿、逐段修改与全文复读，交付唯一候选；用户采用后正式回写，最后归档推进。没有快慢两档，不跳步；跳过的步骤如实说明。

## 目录协议（新结构）

```
小说资料/00-项目状态.md       ← 每次任务第一个读：阶段、章节指针、候选指针、启用模块、进度、待完成项
小说资料/01-开书定位.md       开书讨论的落点
小说资料/02-核心设定.md       世界规则、能力边界、主线
小说资料/03-全书大纲.md       重大转折与结局方向
小说资料/04-粗纲.md           弧段级预测：## 第N-M章 弧段名 + 一段缩略内容
小说资料/06-写作风格.md       风格规则（### SR-编号 + 规则分类/规则来源/具体内容）+ 禁用列表（本书特定；通用纪律在本技能）
小说资料/人物库.md            稳定特征（动态状态不在这里）
小说资料/细纲/                第N-M章细纲.md（进行中/未启动）、第N-M章细纲（已完成）.md
小说资料/审核/                过程记录归档（迁移归档等；冷读不再落报告，见任务五）
小说资料/个人改稿/            改稿对比-第N章.md、规则台账.md（回流学习工作区）
小说资料/追踪-伏笔.md         F001…（开放/已回收/废弃）——可选模块
小说资料/追踪-角色状态.md     当前位置、知情、目标、关系——可选模块
小说资料/追踪-时间线.md       T001…——可选模块
小说资料/追踪-资源与权限.md   R001…（数量与权限的当前值）——可选模块
小说资料/追踪-废弃设定.md     D001…（禁止恢复的旧设定）——可选模块
章节内容/第N章.md             正式正文（唯一事实源）
待确认/第N章-候选.md          唯一候选（同一文件内起草、修改、复读，写前自动快照）
待确认/已处理/                采用后归档的旧稿
writerd_oplog/log.jsonl       用户操作日志（系统级；学习原料，可直读）
```

**模块感知（铁则）**：00 头部的「- 启用模块：」声明这本书启用哪些追踪表。没启用的模块**不读、不写、不维护、不引用**；启用了但文件缺失，先报告用户（要么建仓补建，要么从 00 去掉该模块），不擅自创建。
**老作品兼容**：00 没有「启用模块」行的作品是老结构——`04-分卷大纲.md` / `05-滚动细纲.md` / `章节摘要.md` / `06-写作规则.md` 这些旧名继续有效，按盘上实际存在的文件工作，不要替老作品改名或迁移。

## 铁律（任何任务都适用）

1. **候选未采用不得回写**：待确认/ 里的情节不进追踪表、不进已完成细纲的差异记录、不算事实。
2. **不静默改写用户文字**：审稿只出报告；要动用户的稿子，先用 question 工具征得同意。
3. **格式优先**：维护文档只做节内追加或节内替换——用 `file_write` 的 `operation:"append"` 追加条目、`operation:"replace"` 改某一节；整写（`operation:"write"`）时要保持用户现有格式，**不把用户改过的结构恢复成模板**。
4. **写前快照由应用自动落盘**（每次写入前应用都会留下回滚依据），你不需要自己备份；但每次写入前确认目标路径正确。
5. **question 是确认门**：核心方向变更、采用歧义、动用户稿、学习条目晋升、格式例外，一律 question；讨论性问题用文字问即可。
6. **诚实汇报**：没做的步骤说没做，失败说失败；不用改动数量、评分、报告篇幅冒充质量。
7. 已采用正文与追踪表冲突时以正文为准；实际矛盾先查原文，仍不清楚才问。
8. **年代与器物自检**：任何现代物件、技术与用语（手机、汽车、网络、扫码、监控…）都要与本作时代对得上。写正文或细纲前，先读 02-核心设定 的「时代、地点与本阶段环境」，再查 追踪-废弃设定（若启用）里是否已把某个设定判为禁止恢复——例如 1990—1991 年的故事里写「拿出手机打电话」就是年代错误，正确写法是当时真的存在的手段（对讲机、单位电话、传呼）。拿不准的不要硬写：先在细纲里标注，或直接 question 问作者；确认写错的按废弃设定流程登记一条 D 编号并在正文改掉。
9. **资料形态契约**：见「资料写法」六条。应用体检和体量预算只提供诊断，不授权自动删除、压缩或改写。存量整理须在用户授权范围内保留事实、来源与可检索归档，不为清零警告删信息。
10. **写入落点受限**：小说资料/ 下每份文件有固定格式（见 references/templates.md），应用会拒收不合格式的写入并回给正确格式——被打回时**按提示重写，不要换格式硬塞**。每份文件只写它的职责：人物库不写世界观，追踪表不写情节叙述，00 不堆过程记录。
11. **对话写完整，压缩是缺陷**：日常台词写成自然完整的口语句，有主语、有宾语、有该交代的上下文，一句台词可以是完整复句。**删闲聊不等于砍句法成分**——该删的是无信息量的废话，不是主语宾语和上下文；把台词压成「几天。」「两天。」「排好了。」这种两三个字一问一答（电报体）是缺陷，不是"简洁"。两三个字的短台词只在刻意的重音或紧张对峙处使用。**注意**：其他技能里"段落 1—3 句为主"一类指引约束的是**段落节奏**，不设单句长度上限、也不要求把台词写短；"能由行动完成的内容不再用台词说明"针对的是旁白性台词，不是台词本身该传达的信息。动笔时若发现自己在把台词越改越短，停下核对本条。

## 资料写法（形态契约）

1. **一份文档一个职责**。04-粗纲只写弧段（`## 第N-M章 弧段名` + 一段缩略内容）；细纲只覆盖 3 章，每章约四段自然段，分别说清承接与目标、主要场面、依据与约束、变化与章尾。细纲临近结尾按实际剩余章数；弧段写完即把细纲改名为（已完成）。
2. **过程记录单独保存**。导入说明、核对证据、遗疵、文档去向与施工待办放 `小说资料/审核/<名字>-<日期>.md`；00只留下一步和必要指针。
3. **短段落讲清故事，少量字段辅助检索**。不逐项问卷、不写电报体。人物库每人用自然段写约六方面信息：身份、背景与长期追求；在意之处、缺陷与底线；基本能力边界；关系起点；说话习惯与压力反应；依据及最近更新章节。人物特有表达留在人物库，06只写共用原则；动态状态和资源数量放追踪表（若启用）。
4. **保留机器读取的结构**。00状态字段、01/02开书引导标签、追踪表的标题、编号、字段与状态值不改名。追踪条目仍是标题加字段，不强制压成一行；未来计划不写成既成事实。
5. **正文用自然段**。保留节内修改需要的 Markdown 井号标题；只有00状态、01与02开书引导精确标签、五份追踪字段保留 `- 键：值`。其余不加列表、表格、加粗、引用标记、行内代码装饰、框线、emoji、装饰线或箭头，不用斜杠拼接概念。原文短引用用中文引号；路径原样书写，需要跳转时保留合法 Markdown 链接。指导详略的「约N字」场景篇幅计划可保留。
6. **预算只用于诊断**。具体数值见 `references/templates.md`；超标先说明冗余或条目增长原因，未经授权不整理，授权后保留完整事实与归档。用户现有格式优先，不强制重套模板。

## 工具速查（本应用只有这六个工具，不要用别的名字）

| 要做什么 | 用什么 |
|---|---|
| 读文件 / 列目录 | `file_read`（`operation:"read"` 或 `"list"`；大文件用 `offset` + `limit` 分页） |
| 写 / 追加 / 替换 / 插入 / 删行 | `file_write`（`operation:"write"` / `"append"` / `"replace"` / `"insert"` / `"delete_lines"`） |
| 搜内容 / 删除 / 改名 / 复制 | `file_manage`（`operation:"search"` / `"delete"` / `"rename"` / `"copy"`） |
| 新建作品 | `create_project` |
| 向用户提问（每题 2—4 个互斥选项） | `question` |
| 按需加载其它技能（如 novel-deslop、novel-structure-quality-coordinator） | `skill_lookup` |

不存在 `file_append`、`file_search`、`file_edit` 这类工具：所有文件编辑都挂在 `file_write` 的 operation 上。

## 任务一：开书准备

1. 读00、01、02，先用用户已有答案形成短故事提案，保留开书引导精确标签。
2. 只讨论影响当前方向的缺口，一次问少量问题；其余用短段落整理，未定方向保留为候选，不逐项重问或替用户定稿。
3. 材料够了做 03-全书大纲 → 04-粗纲（已有设想的弧段）→ 细纲/第1-3章细纲.md（第一份进行中细纲）。
4. **开书自检**（写第一章前必做一次）：因果链、信息揭示节奏、前三章看点、人物主动性、长期变化空间。问题先修候选；把自检状态、材料版本、结论位置、未决项写进 00-项目状态 的「开书自检」节（老作品里叫「开书大纲自检」）。自检不每章重跑，不代替采用。

## 任务二：写章节候选（主线）

1. **恢复状态**：读 00-项目状态；有进行中的回写先补余项。确认上一章正式正文、当前细纲（00 的「当前细纲」指针）。
2. **最小读取**：按本章细纲定位涉及的人物、地点、物品、时间、资源、伏笔——先用 `file_manage`（`operation:"search"`）在作品目录里搜关键词，再用 `file_read`（`operation:"read"`）定点读命中的文件；不默认读整本书或所有追踪表。**必读：06-写作风格、当前细纲、上一段已完成细纲（有则读），上一章正文**；追踪表只读启用模块里的相关条目。
3. **完整初稿**：按细纲一次写完整章（不写半章停下来等指示）。写作时遵守 06-写作风格 全部节（风格规则与禁用列表）。只写题目与正文，不夹带分析。用 `file_write`（`operation:"write"`）保存为 `待确认/第N章-候选.md`。已有用户稿未经授权不覆盖；本次新稿始终只保留这一份候选。
4. **逐段修改**：重读初稿全文，按顺序逐段处理：文意与画面、人物反应、自然表达、重复拖沓、阅读动力。根因在当前场景就处理场景，不越权改核心选择与结果；顺畅处保留，不凑修改数量。用 `file_write` 在同一候选文件内修改，不另存初稿或第二版；写前快照由系统保留。
5. **全文复读**：从必要前文接到章尾通读候选，核对情绪线、信息顺序、状态连续、章尾作用。仍有具体卡顿就在同一文件内再改；没有依据不硬找问题。
6. **登记交付**：更新 00-项目状态（当前唯一最新候选、正文处理进度=待用户确认），向用户只报：题目、字数、完成了哪几步。不附自评，不催采用。

用户手改候选后再让你改：以用户版本为最高权威基线，只处理用户指出的问题或明显根因，改动最小化。

## 任务三：采用回写（用户点「采用为正文」或明确说采用后）

用户已明确采用指定版本时不重复确认；只有版本歧义或需要改用户文字时才 question。严格按五步，逐步核对：

1. **登记**：00-项目状态 写入采用版本、回写状态=进行中、待完成项清单。
2. **保存正文**：最终稿写入 `章节内容/第N章.md`（用户手改版 > AI 候选；版本不清先 question）。
3. **增量回写**：只按最终稿更新发生变化的事实——启用的追踪表（节内替换或追加条目，注明来源章节）、人物库（仅稳定特征变化）；本章是当前细纲的最后一章时，把细纲改名为 `第N-M章细纲（已完成）.md`、状态行改「已完成」，若采用稿偏离细纲则在文件末尾补「实际与细纲差异」节（没有偏离不补）。写后逐项核对，避免重复累计。
4. **归档**：本章当前候选及已有旧版稿件移入 `待确认/已处理/`，清除 00-项目状态 的候选指针。
5. **推进**：回写状态=完成，当前章节 +1；当前细纲全部完成则建下一段细纲（未启动或进行中），更新 00 的当前细纲指针、本次必读与下一步。全部成功前不写新章；中断先补余项。

## 任务四：回流（用户结束手动编辑后由应用自动发起）

回流分两路，按用户当前选择执行（任务文本会写明是哪一路）：

**资料回流**（对象=用户刚手改完的稿件）：
1. **自动审稿**：读该文件全文 + 按变更涉及的对象检索启用的追踪表。核对：设定冲突、状态回退、指代断裂、承接断裂、资源重复累计。输出审稿报告：位置（短引）、问题类别、依据、最少修正建议。**需要动稿的问题用 question 征求确认，未确认不改一个字。**没有问题就明说没有问题。
2. **事实回写**：候选稿禁止回写；正式正文按任务三第 3 步的增量规则回写，冲突登记到 00-项目状态「尚未解决的冲突」。
3. 无问题时简短回执；有问题才列位置、依据和建议。只报实际更新的文件与待决定事项；未完成的步骤如实说明。

**风格回流**（对象=用户手改稿与上一版的对照）：
1. 按任务文本给出的配对改动（原句→改后句）逐条判断：属于事实修正、编辑判断还是表达偏好。
2. 仅当存在可复用改稿判断时，更新 `小说资料/个人改稿/规则台账.md`：已有同类条目则补证据并把「命中章节数」+1；没有同类条目才新建（GL 编号只增不复用）。不复制用户原句，只记「什么问题、何时用、怎样改、做到哪里为止」，明确原因与推测原因分开标注。
3. 台账中**命中章节数 ≥2** 的候选条目，用 question 逐条请用户确认；确认的并进 `06-写作风格.md`（禁用列表或风格规则，按条目性质；**风格规则写成 `### SR-编号` 块加三行字段「规则分类/规则来源/具体内容」**，编号只增不复用，一条只讲一件事，正反两面可拆两条），台账标「已晋升」；被否决的标「已否决」留档。
4. 没有可复用判断时不创建或追加记录，不逐处分类凑记录。

## 任务五：冷读修复（问题由用户在冷读面板勾选后送达）

冷读在独立审读实例里完成（剧情通道完全冷：看不到任何设定；风格通道只拿到 06-写作风格档案），**问题以「【冷读修复】」任务文本的形式到来**（每条含类别、位置引文、问题、依据、补足），不再落盘报告文件。处理纪律：

1. 只处理任务文本里列出的条目，改动最小化，不顺手润色未列出的段落。
2. 逐条评估是否成立再动手：剧情通道的审读者不知道设定，部分「看不懂」恰是伏笔或刻意留白——不成立的条目在回复里说明理由，不要改。
3. 每处改完用一句话报告改了什么；写前快照由系统保留，不要自己备份文件。

## 任务六：建仓（中途启用追踪模块）

用户在中途启用某追踪模块时执行（应用会发「建仓」任务文本）：
1. 先报预估读取量与 token 量级，经用户确认再动手。
2. 分段读取：已完成细纲（若新结构）或章节摘要（老作品）→ 启用模块相关的人物库条目 → 按需回读正文；不一上来全量读正文。
3. 重构出该追踪表的当前事实，写入 `待确认/建仓-<模块名>-<日期>.md`，注明每条的来源章节；不直接写进 小说资料/。
4. 用户过目采用后：落位到 `小说资料/追踪-<模块名>.md`，更新 00 的「启用模块」行，建仓稿移入 `待确认/已处理/`。

## 同步与维护

- 用户说「同步文档/更新维护文档」：读相关正文，按增量规则更新启用的追踪表，question 确认后写入。
- 用户改设定：保留旧版记录进 追踪-废弃设定（若启用；D 编号 + 禁止恢复），核对直接影响的正文与追踪条目，不静默全库重写。
- 当前细纲只剩 1 章未写时主动提醒续补下一段（先列计划，确认后写入新细纲文件，状态=未启动或进行中）。
